# V1 — Current Implementation

## 1.1 Architecture Overview

### Service Type
**Single-process monolithic microservice.** The entire application (HTTP server, cron, webhook processing) runs in one Node.js process. There is no worker process separation or internal queue.

### Tech Stack

| Layer | Technology | Version |
|---|---|---|
| Runtime | Node.js | LTS (implied) |
| HTTP Framework | Express | ^5.2.1 |
| ORM | Prisma Client | ^6.19.2 |
| Database | PostgreSQL (Supabase-hosted) | — |
| HTTP Client (internal) | `undici` | ^7.22.0 |
| HTTP Client (outgoing webhooks) | `axios` | ^1.13.6 |
| Auth hashing | `bcryptjs` | ^3.0.3 |
| Request deduplication hash | `fast-json-stable-stringify` + `crypto` | — |
| Scheduling | `node-cron` | ^4.2.1 |
| Security headers | `helmet` | ^8.1.0 |
| CORS | `cors` | ^2.8.6 |
| Logging | `morgan` (combined format) | ^1.10.1 |
| ID generation | `uuid`, `cuid` | — |
| Validation | `express-validator` | ^7.3.1 |

### Entry Point & Process Bootstrap (`src/index.js`)
- Loads environment via `dotenv` selecting `.env.development` or `.env.production` based on `NODE_ENV`
- Performs a `SELECT 1` DB health check before binding the HTTP server — **hard-exits on failure** (`process.exit(1)`)
- Registers `SIGTERM` / `SIGINT` handlers that call `prisma.$disconnect()` for graceful shutdown
- Starts `idempotencyCron` at bootstrap (always-on, same process)
- Listens on `PORT` (default `9000` in development, `3000` as fallback)

### Directory Structure

```

├── Cron/               # node-cron jobs

│   └── webhookHandlers/ # Event-specific Tilled webhook processors
├── utils/

```

### Deployment Assumptions (Inferred)
- Hosted on **Render** (referenced in CORS whitelist: `creditor-backend-hg94.onrender.com`)
- Frontend checkout page hosted on **Netlify** (`payment-checkoutt.netlify.app`)
- Database on **Supabase** with PgBouncer connection pooling (`port 6543`)
- Environment variables managed per-deploy via `.env.production` / `.env.development`
- No containerisation or orchestration configuration present in the repo

## 1.2 Payment Flow

The service handles two distinct payment paths: **One-Time** (Tilled Checkout Session) and **Recurring/Subscription** (Tilled.js embedded form).

### Middleware Chain for `POST /api/payments`

```
Request
  → authenticate          (auth.js)          — prefix lookup + bcrypt verify + rate-limit
  → requirePermissions    (requirePermissions.js) — checks ["charge"] on key.permissions
  → validateCreatePayment (validatePaymentRequest.js) — express-validator rules
  → requireIdempotencyKey (requireIdempotencyKey.js)  — enforces header presence
  → idempotency           (idempotency.js)   — optimistic lock + replay cache
  → controller.createPayment
```

### One-Time Payment Flow (`plan.billingType === "ONE_TIME"`)

```
1. [Auth Middleware]
   - Extract x-api-key header
   - Resolve key prefix → DB lookup (apiKey.dao.getApiKeysByPrefix)
   - bcrypt.compare(apiKey, keyHash) — iterate matching prefix rows
   - Check expiresAt, check rate limit via RateLimitService.checkRateLimit()
   - Resolve delegate mode (if key.permissions includes "delegate")
   - Attach req.productId, req.apiKey, req.permissions

2. [Idempotency Middleware]
   - Check if referenceId already has a PAID order → 200 early-return
   - SHA-256 hash of {body, query} → requestHash
   - Atomic prisma.idempotencyKey.create() → IN_PROGRESS lock
   - On conflict: lookup existing record, check TTL, replay COMPLETED, block IN_PROGRESS

3. [service.createPayment(productId, data, {idempotencyKey})]
   a. Validate productPlanId: prisma.productPlan.findFirst({id, productId, isActive})
   b. DB Transaction (prisma.$transaction):
      - productUserDAO.upsertProductUser() — find or create ProductUser by externalUserId
      - orderDAO.getOrderByReferenceId() — check for existing order
      - If order exists: inspect latest payment status
        · SUCCEEDED / PROCESSING → return duplicate:true
        · FAILED / CANCELLED / INITIATED → create new Payment(INITIATED), allow retry
      - If no order: orderDAO.createOrder() with status=CREATED
        · Race-condition guard: catch P2002 unique constraint → handle __duplicate flag
      - paymentDAO.createPayment() with status=INITIATED
      - idempotencyKey.updateMany() to link orderId + paymentId (atomic within tx)

   c. Tilled Customer resolution:
      - If productUser.tilledCustomerId exists → TilledService.getCustomer()
      - Else → TilledService.createCustomer() + productUserDAO.updateTilledCustomerId()

   d. Platform fee calculation:
      - isEbook = plan.product.name.toLowerCase() === "ebook"
      - platformFee = isEbook ? Math.round(amount * 0.20) : null

   e. TilledService.createCheckoutSession({
        customer_id, line_items, mode: "payment",
        success_url, cancel_url,
        payment_intent_data: { description, setup_future_usage, metadata, platform_fee_amount }
      }, tilledAccountId)

   f. On success (statusCode < 400):
      - prisma.payment.update({status: "PROCESSING", tilledPaymentId: checkoutSession.payment_intent_id})
      - Return { checkoutUrl, payments:[{status:"PROCESSING"}], duplicate:false }

4. [Idempotency Middleware — response intercept]
   - res.json() is monkey-patched to inspect body.status
   - Maps PROCESSING → IN_PROGRESS, SUCCEEDED → COMPLETED, FAILED → FAILED
   - Updates idempotencyKey record with final status + responseBody

5. [Tilled Webhook — POST /api/webhooks/tilled]
   - Tilled calls back on payment_intent.succeeded / payment_failed / canceled
   - webhook.controller.js: verifies HMAC-SHA256 tilled-signature header
   - Sends 200 immediately, processes async via processWebhookEventAsynchronously()
   - webhookEventDAO.createEvent() for deduplication (@@unique on [eventType, tilledId])
   - paymentIntent.handler.js: updates Payment → SUCCEEDED + Order → PAID in transaction
   - updateIdempotencyStatus() via raw SQL (workaround for Prisma v6 enum in transaction)
   - webhookDispatcher.dispatch() → fires outgoing webhooks to product backends
```

### Subscription Flow (`plan.billingType === "RECURRING"`)

```
PHASE 1 — Initiation (POST /api/payments)
  Same steps 1–3c as above, then:
  - Build URL: FRONTEND_PAYMENT_PAGE_URL + URLSearchParams({orderId, tilledAccountId,
    publishableKey, amount, currency, email, customer_name})
  - Return checkoutUrl pointing to Netlify frontend (Tilled.js embedded form)
  - Payment stays INITIATED (no PROCESSING transition)

PHASE 2 — Confirmation (POST /api/payments/confirm)
  - Frontend (Tilled.js) tokenises card → gets payment_method_id
  - POST { orderId, payment_method_id, tilledAccountId, productId } to /confirm

  service.confirmSubscriptionPayment():
  Step 1: orderDAO.getOrderById() — verify productId match, status != PAID,
          orderType == SUBSCRIPTION, plan.billingType == RECURRING
  Step 2: TilledService.attachPaymentMethodToCustomer(paymentMethodId, tilledCustomerId)
          - On "already associated" error: list customer PMs, match by last4+exp,
            fallback to most recent card PM → reuse existing paymentMethodId
  Step 3: TilledService.createSubscription({billing_cycle_anchor, currency,
          customer_id, interval_count, interval_unit, payment_method_id, price, metadata})
  Step 4: DB Transaction:
          - paymentDAO.updatePayment(SUCCEEDED, tilledPaymentMethodId)
          - orderDAO.updateOrder(PAID)
          - subscriptionDAO.upsertSubscription() with mapped status + safe date parsing
          - orderDAO.updateOrder({subscriptionId}) — link subscription
          - raw SQL update of IdempotencyKey → COMPLETED
  Step 5: Tilled fires subscription.created webhook →
          subscription.handler.handleSubscriptionCreated() upserts DB + dispatches outgoing webhook
```

## 1.3 API Design

### Authentication
All protected routes require:
```
x-api-key: pk_{env}_{productCode}_{32-byte-hex}
```
- Key never stored in plaintext — only a `bcryptjs` hash at salt rounds 10
- `keyPrefix` (everything up to and including the last `_`) is stored for fast DB pre-filter
- Lookup: `getApiKeysByPrefix()` → iterate → `bcrypt.compare()`

### Permission Model
Each API key carries a `String[]` permissions array. Valid values: `charge`, `refund`, `read`, `delegate`.  
`requirePermissions(["charge"])` middleware enforces presence of all listed permissions.

### Delegate Mode
A key with the `delegate` permission can make payments on behalf of any product by passing `productCode` or `productId` in the request body. The auth middleware resolves the target `productId` and replaces `req.productId`. Used by the shared Netlify checkout frontend.

### Endpoint Catalogue

## 1.4 Data Layer

### Database
PostgreSQL hosted on **Supabase**, connected via **PgBouncer** connection pooling (`port 6543`). ORM is **Prisma v6** with `prisma-client-js` generator.

### Core Models

#### `Product`
Top-level tenant entity. Each product (`lms`, `ebook`, `ppt`, etc.) is identified by a unique `code`. All other models hang off `productId`.

#### `ApiKey`
- `keyHash` (bcrypt, unique) — the actual key, never stored plain
- `keyPrefix` — indexed for fast prefix-based lookup (`getApiKeysByPrefix`)
- `permissions String[]` — per-key capability list
- `rateLimitPerMin Int` — per-key window limit (default 100)
- `environment` — `production` | `staging` | `development`

#### `ProductUser`
Bridges external user IDs (from calling products) to internal users.
- `@@unique([productId, externalUserId])`
- `tilledCustomerId` — cached Tilled customer ID to avoid re-creation

#### `Order`
Central transaction record.
- `amount Int` — stored in **smallest currency unit (cents)**
- `currency String` — default `"USD"` (hardcoded default; no multi-currency routing yet)
- `status OrderStatus` — `CREATED | PENDING | PAID | FAILED | CANCELLED | REFUNDED | PARTIALLY_REFUNDED`
- `orderType OrderType` — `ONE_TIME | SUBSCRIPTION | CANCEL | REFUND | OTHER`
- `@@unique([productId, referenceId])` — prevents duplicate orders per external reference
- `metadata Json?` — stores arbitrary `extraData` from caller

#### `OrderItem`
Line-item breakdown. `price Int` per unit in smallest currency unit.

#### `Payment`
- `tilledPaymentId String? @unique` — Tilled payment_intent ID
- `tilledPaymentMethodId String?` — saved for subscription renewal
- `status PaymentStatus` — `INITIATED | PROCESSING | SUCCEEDED | FAILED | CANCELLED`
- `rawRequest Json?`, `rawResponse Json?` — full Tilled API payloads stored for audit
- `method PaymentMethod` — `CARD | ACH | WALLET`

#### `Refund`
- `tilledRefundId String? @unique`
- `status RefundStatus` — `PENDING | SUCCEEDED | FAILED | CANCELLED`

#### `Subscription`
- `tilledSubscriptionId String? @unique`
- `status SubscriptionStatus` — `ACTIVE | PENDING | INACTIVE | CANCELLED | PAST_DUE | TRIAL`
- `currentPeriodStart / currentPeriodEnd DateTime`
- `cancelAtPeriodEnd Boolean`

#### `IdempotencyKey`
Full idempotency record per `(productId, key, method, path)`.
- `requestHash String` — SHA-256 of `{body, query}` — detects same-key/different-payload abuse
- `status IdempotencyStatus` — `IN_PROGRESS | COMPLETED | FAILED | CANCELLED`
- `responseBody Json?`, `responseStatusCode Int?` — cached for replay
- `expiresAt DateTime` — configurable TTL (default 3000s / ~50 min)
- `orderId / paymentId` — linked after order creation for webhook-driven updates

#### `WebhookEvent`
Deduplication store for incoming Tilled webhooks.
- `@@unique([eventType, tilledId])` — prevents double-processing

#### `ProductWebhookConfig`
Per-product, per-event outgoing webhook config.
- `triggerEvent String` — e.g. `"payment_intent.succeeded"`
- `authType OutgoingAuthType` — `BEARER_TOKEN | API_KEY_HEADER | BASIC_AUTH | HMAC_SIGNATURE | NONE`
- `authSecret String?` — stored in plaintext (⚠️ security gap)
- `maxRetries Int` — default 3, `retryDelayMs Int` — default 1000ms

#### `OutgoingWebhookDelivery`
Per-attempt delivery log for each outgoing webhook dispatch.

#### `AuditLog`
Structured audit trail with `AuditEventType` enum covering order, payment, refund, subscription, API key, and webhook events.

#### `RateLimitTracker`
DB-backed sliding-window rate limiter per `(apiKeyId, windowStart)`.
- `@@unique([apiKeyId, windowStart])` — one row per minute window

### Idempotency Cleanup Cron
`src/Cron/idempotencyCron.js` runs every minute via `node-cron`:
- Deletes `COMPLETED` records older than **2 minutes**
- Deletes `IN_PROGRESS` records older than **50 minutes** (stale locks)

## 1.5 Gateway Integration — Tilled

### Integration Method
**Raw HTTP via `undici`** — no official Tilled SDK. All calls go through `TilledService._makeRequest()`:

```js
static async _makeRequest(endpoint, method, body, tilledAccountId) {
  const headers = {
    'tilled-api-key': process.env.TILLED_SANDBOX_SECRET_KEY,
    'Content-Type': 'application/json'
  };
  if (tilledAccountId) headers['tilled-account'] = tilledAccountId;
  const { statusCode, body: responseBody } = await request(
    `${process.env.TILLED_SANDBOX_BASE_URL}${endpoint}`, { method, headers, body }
  );
  return { statusCode, data: await responseBody.json() };
}
```

### Base URL
`TILLED_SANDBOX_BASE_URL = https://sandbox-api.tilled.com/v1`

### Implemented TilledService Methods

| Method | Tilled Endpoint | Used In |
|---|---|---|
| `createCheckoutSession()` | `POST /checkout-sessions` | `createPayment` one-time |
| `createCustomer()` | `POST /customers` | `createPayment` |
| `getCustomer()` | `GET /customers/:id` | `createPayment` |
| `listCustomers()` | `GET /customers` | Admin |
| `createSubscription()` | `POST /subscriptions` | `confirmSubscriptionPayment` |
| `cancelSubscription()` | `POST /subscriptions/:id/cancel` | `cancelSubscription` |
| `attachPaymentMethodToCustomer()` | `PUT /payment-methods/:id/attach` | `confirmSubscriptionPayment` |
| `detachPaymentMethod()` | `PUT /payment-methods/:id/detach` | Cleanup on failure |
| `getPaymentMethod()` | `GET /payment-methods/:id` | Duplicate card resolution |
| `listCustomerPaymentMethods()` | `GET /payment-methods?customer_id=&type=card` | Duplicate card resolution |
| `createRefund()` | `POST /refunds` | `refundPayment` |
| `verifyWebhookSignature()` | — (local HMAC) | Webhook controller |
| `getAccount()` | `GET /accounts` | Admin |
| `createConnectedAccount()` | `POST /accounts/connected` | Admin |

### Webhook Signature Verification
`TilledService.verifyWebhookSignature(header, rawBody)`:
- Parses `tilled-signature: t=<timestamp>,v1=<hex>` header
- Computes `HMAC-SHA256(webhookSecret, "<timestamp>.<rawBody>")`
- Uses `crypto.timingSafeEqual()` for constant-time comparison
- `express.json()` captures `req.rawBody` via the `verify` callback in `app.js`

### Error Handling
- All `_makeRequest` calls return `{ statusCode, data }` — callers check `statusCode >= 400`
- No automatic retries on gateway calls from the service layer (retries exist only in outgoing webhook dispatcher)
- Duplicate card attachment handled with multi-step fallback: exact match by `last4+exp`, then `last4-only`, then most-recent card PM
- Orphaned payment method cleanup: `detachPaymentMethod()` called on subscription creation failure

### Outgoing Webhook Dispatcher (`webhookDispatcher.service.js`)
- Fired after each Tilled webhook is processed
- Reads `ProductWebhookConfig` for `(productId, triggerEvent, isActive)`
- Retry loop: up to `config.maxRetries` (default 3) with `config.retryDelayMs` (default 1000ms) delay
- 4xx responses abort retry immediately (permanent client error)
- Every attempt (success or failure) logged to `OutgoingWebhookDelivery`
- Auth types supported: `BEARER_TOKEN`, `API_KEY_HEADER`; `BASIC_AUTH` and `HMAC_SIGNATURE` entries exist in the enum but are not yet implemented in `buildHeaders()`

## 1.6 Security — Current State

### Implemented
| Control | Implementation |
|---|---|
| API Key hashing | `bcryptjs` with 10 salt rounds — plaintext never persisted |
| Constant-time key comparison | `bcrypt.compare()` is inherently timing-safe |
| Webhook signature | HMAC-SHA256 + `crypto.timingSafeEqual()` |
| Rate limiting | DB-backed per-key per-minute window via `RateLimitTracker` |
| CORS restriction | Explicit allowlist in `corsLinks.origin` |
| Security headers | `helmet()` applied globally |
| Permission enforcement | Per-route `requirePermissions()` middleware |
| Idempotency | Prevents duplicate charges via optimistic locking + payload hashing |
| Admin routes | `x-admin-secret` header check against `process.env.ADMIN_SECRET` |
| Graceful shutdown | SIGTERM/SIGINT handlers with `prisma.$disconnect()` |
| Raw body capture | `req.rawBody` captured in `express.json()` verify callback |

### Weaknesses / Gaps

| Issue | Risk | Location |
|---|---|---|
| Admin routes (`/api/keys`, `/api/products`, `/api/crud`, `/api/product-plan`) are **unprotected** | Anyone can create/delete API keys | `app.js` lines 81–84, noted as TODO |
| `authSecret` in `ProductWebhookConfig` stored **in plaintext** in PostgreSQL | Outgoing webhook tokens exposed on DB compromise | `prisma/schema.prisma` |
| Tilled sandbox credentials committed in `.env.development` | Key leakage if repo is public | `.env.development` |
| `ADMIN_SECRET` committed in `.env.development` | Admin panel takeover | `.env.development` |
| `auditLogger` middleware is **commented out** | No per-request audit trail | `app.js` line 6, 29 |
| Rate limiting stored in DB, not in-memory cache | Race conditions possible under concurrent load; DB becomes bottleneck | `rateLimit.service.js` |
| No HTTPS enforcement or HSTS headers | Depends entirely on hosting layer | — |
| No input sanitisation beyond express-validator (no XSS/SQLi guards) | Low risk via Prisma parameterisation, but raw `$executeRaw` used in idempotency update | `paymentIntent.handler.js` |
| `BASIC_AUTH` and `HMAC_SIGNATURE` outgoing auth types are enum values but **not implemented** | Config set to these types silently sends no auth | `webhookDispatcher.service.js` |
| No replay-attack protection on webhook receiver (only signature check, no timestamp window) | Old intercepted Tilled webhooks could be replayed | `webhook.controller.js` |

## 1.7 V1 Limitations

### 1. Hard-Coded Single Gateway
`TilledService` is directly `require()`d throughout `payments.service.js` and `subscription.service.js`. There is no abstraction layer. Swapping or adding a gateway requires modifying core business logic.

### 2. Single Currency (Effectively USD-Only)
`Order.currency` defaults to `"USD"` and is derived from `ProductPlan.currency`. There is no currency conversion, no normalisation layer, and no validation that incoming currency matches gateway capabilities.

### 3. DB-Backed Rate Limiting Without Caching
`RateLimitService` writes to `RateLimitTracker` on every request. Under burst traffic this creates write contention. The fail-closed behaviour (`return { limited: true }` on any DB error) is safe but can cause false positives.

### 4. Synchronous Webhook Processing (Partially)
The webhook controller detaches HTTP response handling correctly (200 returned immediately), but `processWebhookEventAsynchronously` runs in the same Node.js event loop with no backpressure, queue, or worker isolation. A spike in events can block the main thread.

### 5. No Horizontal Scaling Path
- In-process `node-cron` job will duplicate across multiple instances
- DB-backed idempotency locking using `prisma.idempotencyKey.create()` would work across instances, but the cron cleanup would race
- No sticky-session or distributed lock awareness

### 6. `BASIC_AUTH` / `HMAC_SIGNATURE` Outgoing Webhook Auth Not Implemented
Schema defines these enum values but `buildHeaders()` only handles `BEARER_TOKEN` and `API_KEY_HEADER`.

### 7. Webhook Retry Strategy is Synchronous / In-Process
`attemptDelivery()` loops with `setTimeout(resolve, delay)` inside the same async execution. If the process restarts mid-retry, all pending retries are lost.

### 8. Admin Routes Entirely Unprotected
Noted explicitly in `app.js` as a TODO. As-is, any actor who can reach the server can generate API keys, delete products, or view all data.

# V2 — Planned System

> **Status: Planned.** Nothing in this section is currently implemented in the codebase.

## 2.1 Proposed Architecture Changes

### Core Principle: Gateway Abstraction via Strategy Pattern

The primary change is to extract all Tilled-specific code behind a gateway interface so that any gateway can be swapped or added without modifying `payments.service.js`.

#### Proposed File Structure

```
src/
├── gateways/
│   ├── IGateway.js             # Abstract interface (contract)
│   ├── TilledGateway.js        # Wraps existing TilledService
│   ├── StripeGateway.js        # Future
│   ├── RazorpayGateway.js      # Future
│   └── GatewayFactory.js       # Resolves which gateway to use
```

#### `IGateway.js` — Interface Contract

```js
/**
 * All gateway implementations must implement these methods.
 * Throw standardised GatewayError objects — never expose raw gateway errors upward.
 */
class IGateway {
```

## 2.3 Multi-Currency Handling

### Storage Format
**Already correct in V1:** `amount Int` (smallest currency unit — cents, paise, etc.). Do **not** change to `Decimal` or `Float` — integer arithmetic is the industry standard for financial values.

### Currency Normalisation Strategy

```js
// Planned utility: src/utils/currency.js
const CURRENCY_MINOR_UNIT_MULTIPLIERS = {
  USD: 100,  // cents
  EUR: 100,
  GBP: 100,
  INR: 100,  // paise
  JPY: 1,    // yen has no minor unit
  KWD: 1000, // fils
};

function toMinorUnit(amount, currency) {
  const multiplier = CURRENCY_MINOR_UNIT_MULTIPLIERS[currency.toUpperCase()];
  if (!multiplier) throw new Error(`Unknown currency: ${currency}`);
  return Math.round(amount * multiplier);
}

function fromMinorUnit(amount, currency) {
  const multiplier = CURRENCY_MINOR_UNIT_MULTIPLIERS[currency.toUpperCase()];
  return amount / multiplier;
}
```

- Store the exchange rate used at the time of the order in `Order.metadata` for audit

## 3.1 Asynchronous Architecture

### Current Problem
`processWebhookEventAsynchronously()` in `webhook.controller.js` runs in the same Node.js event loop. It is "async" only in that it doesn't block the HTTP response, but it still competes for the same CPU and DB connections as incoming requests.

### Recommended: Separate Queue-Based Worker

#### Option A — BullMQ + Redis (recommended for self-hosted)

```
Incoming Tilled Webhook
  → POST /api/webhooks/tilled
  → Signature verified (sync, fast)
  → Job enqueued to Redis via BullMQ
  → 200 returned immediately

BullMQ Worker Process (src/workers/webhookWorker.js)
  → Dequeues job
  → processWebhookEvent(job.data)
  → paymentIntent.handler / subscription.handler
  → webhookDispatcher.dispatch()
```

```js
// src/workers/webhookWorker.js
const { Worker } = require('bullmq');
const { processWebhookEvent } = require('../services/webhookProcessor.service');

const worker = new Worker('tilled-webhooks', async (job) => {
  await processWebhookEvent(job.data);
}, {
  connection: { host: process.env.REDIS_HOST, port: process.env.REDIS_PORT },
  concurrency: 5,
});

worker.on('failed', (job, err) => {
  console.error(`Job ${job.id} failed:`, err.message);
});
```

#### Option B — AWS SQS (recommended for managed infrastructure)

```
POST /api/webhooks/tilled
  → sqs.sendMessage({ QueueUrl, MessageBody: event, MessageDeduplicationId: event.id })
  → 200 returned

Lambda / ECS consumer
  → Polls SQS
  → Processes event
  → Deletes message on success
  → On failure: message returns to queue (visibility timeout)
  → After maxReceiveCount: moves to DLQ
```

### Event-Driven Payment Lifecycle

Introduce internal events for payment state transitions:

```
ORDER_CREATED    → triggers: send confirmation email (future)
PAYMENT_INITIATED → triggers: start timeout watchdog
PAYMENT_SUCCEEDED → triggers: dispatch outgoing webhooks, update idempotency
PAYMENT_FAILED   → triggers: dispatch failure webhook, alert
SUBSCRIPTION_CREATED → triggers: notify LMS/Ebook backends
SUBSCRIPTION_CANCELLED → triggers: revoke access
```

## 3.3 Throughput Optimisation

### Horizontal Scaling — Making the Service Stateless

Current stateful components that block scaling:

| Component | Problem | V3 Fix |
|---|---|---|
| `node-cron` idempotency cleanup | Runs in every instance → duplicate deletes | Move to a dedicated cron service or use DB-native scheduled jobs (pg_cron on Supabase) |

### Rate Limiting — Redis Sliding Window

```js
// src/services/rateLimit.service.js (V3)
const redis = require('../config/redisClient');

async checkRateLimit(apiKeyId, limitPerMin) {
  const key = `rl:${apiKeyId}:${Math.floor(Date.now() / 60000)}`;
  const count = await redis.incr(key);
  if (count === 1) await redis.expire(key, 60);
  return {
    limited: count > limitPerMin,
    remaining: Math.max(limitPerMin - count, 0),
    retryAfter: 60 - (Date.now() % 60000) / 1000
  };
}
```

### Outgoing Webhook Secret Encryption

```js
// src/utils/encryption.js
const crypto = require('crypto');
const ALGORITHM = 'aes-256-gcm';
const KEY = Buffer.from(process.env.ENCRYPTION_KEY, 'hex'); // 32-byte key from secrets manager

function encrypt(plaintext) {
  const iv = crypto.randomBytes(12);
  const cipher = crypto.createCipheriv(ALGORITHM, KEY, iv);
  const encrypted = Buffer.concat([cipher.update(plaintext, 'utf8'), cipher.final()]);
  const tag = cipher.getAuthTag();
  return `${iv.toString('hex')}.${encrypted.toString('hex')}.${tag.toString('hex')}`;
}

function decrypt(ciphertext) {
  const [ivHex, encHex, tagHex] = ciphertext.split('.');
  const decipher = crypto.createDecipheriv(ALGORITHM, KEY, Buffer.from(ivHex, 'hex'));
  decipher.setAuthTag(Buffer.from(tagHex, 'hex'));
  return decipher.update(Buffer.from(encHex, 'hex')) + decipher.final('utf8');
}
```

# Suggested Improvements Beyond V3

These are practical, production-focused recommendations beyond the V3 scope.

## 1. Implement `BASIC_AUTH` and `HMAC_SIGNATURE` in `buildHeaders()`

This is a V1 bug with minimal effort to fix. The enum values exist in `OutgoingAuthType` and in the schema but `buildHeaders()` in `webhookDispatcher.service.js` silently sends no auth for these types. Fix in V1.5 or earlier.

## 2. Protect Admin Routes Immediately

`/api/keys`, `/api/products`, `/api/product-plan`, and `/api/crud` are noted as TODO in `app.js`. Apply `adminOnly` middleware to all of them. This is a **critical security gap** present since V1 — it should be addressed before V2 work begins.

## 3. Platform Fee Logic Should Be Data-Driven

The `isEbook = plan.product.name.toLowerCase() === "ebook"` check in `payments.service.js` (line 376) is a business rule hardcoded in service code. Move this to `ProductPlan.platformFeePercent` or `Product.platformFeePercent`. This makes the system configurable without deploys.

## 4. Prisma v6 `$executeRaw` Enum Workaround — Long-Term Fix

The raw SQL `CAST(${newStatus} AS "IdempotencyStatus")` in `paymentIntent.handler.js` and `payments.service.js` is a documented Prisma v6 limitation. Track the upstream Prisma issue and remove the workaround when the bug is fixed. Until then, centralise this raw SQL into a single DAO method to avoid it scattering across the codebase.

## 5. API Versioning

All routes are currently unversioned (`/api/payments`). Introduce `/api/v1/payments` now before V2 breaks the contract. Express Router prefixing makes this trivial and allows V1 clients to keep working while V2 is rolled out.

```js
// app.js
app.use('/api/v1/payments', authenticate, paymentsV1Routes);
app.use('/api/v2/payments', authenticate, paymentsV2Routes); // V2 with multi-gateway support
```

## 6. Add Integration / E2E Tests

The `package.json` has `"test": "echo 'no tests' && exit 1"`. At minimum, add:
- Unit tests for `idempotency.js` middleware (the most complex, stateful middleware)
- Integration tests for `createPayment` and `confirmSubscriptionPayment` using Tilled sandbox
- Contract tests for the outgoing webhook payload shape (prevents breaking LMSTP/Ebook integrations silently)

## 7. Database Connection Pooling Configuration

PgBouncer is already in use (port 6543). However, Prisma's connection pool is still separate from PgBouncer. Configure `connection_limit` in `DATABASE_URL` to match the PgBouncer pool size to avoid connection exhaustion under load:

```
DATABASE_URL="...?pgbouncer=true&connection_limit=10"
```

## 8. Graceful Degradation on Rate Limit DB Failure

`RateLimitService.checkRateLimit()` currently fails-closed (returns `limited: true`) on any DB error. This means a brief DB hiccup blocks all API traffic. Consider fail-open for rate limiting if the DB is unreachable (log the error, allow the request through), since the primary DB error will surface through other failures anyway.

## 9. Tenant Isolation Audit

The `productId` scoping pattern is applied consistently across DAOs, but there is no enforcement at the Prisma middleware level. A bug in any service that drops the `productId` filter could leak cross-tenant data. Add a Prisma middleware layer that validates `productId` is present on all sensitive model queries.

## 10. Webhook Delivery SLA Monitoring

`OutgoingWebhookDelivery` already stores per-attempt records. Add a periodic job (or Grafana alert) that:
- Flags orders where all webhook delivery attempts have failed (all records for the order have `success: false`)
- Surfaces these for manual investigation or automatic retry
- Provides an admin endpoint (`GET /admin/webhooks/failed-deliveries`) for ops visibility
